1. Project summary

EcoPlus connects households and businesses to recycling factories. A person photographs a bag, the AI estimates fill level, content type and contamination, a pickup is decided, a shipment gets a QR code and GPS, a driver collects it, an employee weighs it, and the weight (the ground truth) gives points, a warehouse batch and stock. Factories then order clean material. The first version covers households and supermarkets/cafés. Forecasting, heatmaps, IoT bins and a recycling marketplace are future work.

6b. Database explained

How to read it: a table is a list of one kind of thing (users, shipments, batches). Each row is one item. PK is the column that identifies the row. FK is a column that points to a row in another table, which is how tables connect. All ids and values in the example below are made up to show the idea.

The story of one bag through the tables

Every table, column by column

Rules the database must enforce

  • Points are created only from a weighing record, never from a scan or a request.
  • POINTS_LEDGER rows are never edited or deleted. A mistake is fixed with a new row of opposite points.
  • CITIZEN_PROFILE.total_points is a convenience copy. If it ever disagrees with the sum of the ledger, the ledger is right.
  • A shipment has at most one weighing record, and a weighing record needs a positive weight.
  • Saving the weighing, the points, the batch and the stock change happens in one transaction, so all of it succeeds or none of it does.
  • An order item can only take weight from batches that have stock left.

What this means for the plan

  • Bekia is the main competitor. It reports more than 100,000 customers, 25,000 tonnes diverted, and fresh funding. Competing with it on home pickup alone is unlikely to work.
  • Our angle is traceability and quality. Verified weight, contamination check and a direct link to factories, aimed first at businesses with large loads, where the feasibility model is strongest.
  • Informal collectors are a risk. One article describes conflict between startups and the traditional sorters (Zabaleen) in Cairo. Think about working with them, not around them.
  • Next research: try the Bekia and Plstka apps yourself, call 2 or 3 of their business customers, and check their prices per kg.

Main risks

  • Low value per kg. Most recyclables sell for little, so volume and material mix decide profit. Business suppliers with large loads matter more than households.
  • Contamination. Rejected material is cost with no revenue.
  • Driver utilisation. Few stops per driver makes every kg expensive. Merge nearby requests.
  • Price swings. Agree price floors or monthly contracts with factories.
  • Licensing. Confirm with the Waste Management Regulatory Authority and the local district what a collection and storage business needs. Not verified here.
  • Reward cost. Points that cost real money must stay below what the material earns.

10. Database implementation

The ERD becomes a Prisma schema, then migrations, then seed data. These are the rules the database itself should enforce, so a bug in the app cannot break them.

  • Schema. One Prisma model per ERD table, with the foreign keys shown.
  • Migrations. Every change is a migration file in Git. Never edit the database by hand.
  • Seed data. Levels (Bronze to Platinum with multipliers), material types with point factors and prices, one admin, one warehouse, test users for each role.
  • Environments. Separate dev, staging and production databases.
  • Append-only ledger. Block UPDATE and DELETE on POINTS_LEDGER for the app's database user. Corrections are new rows.
  • One transaction for weighing. Weighing record, points, batch and stock update all succeed or all roll back.
  • Constraints. Unique qr_code, weight greater than zero, one weighing per shipment.
  • Indexes. Shipment status and QR, route date, ledger by user, batch by material and warehouse.
  • Backups. Scheduled, stored off the server, and a restore tested once.

Build status (backend, 27 Oct 2026)

Phase 0, Phase 1 and Phase 2 backend are built and tested locally (NestJS, Prisma, PostgreSQL): 125 automated tests pass (66 unit, 59 end to end). Linear: MOA-201 to MOA-207, MOA-212 to MOA-221, MOA-227, and for Phase 2 MOA-228 to MOA-232, MOA-234 and MOA-237 are Done. Not yet verified: Docker build, GitHub CI (no remote yet), Flutter apps, staging on Coolify, the real Google Routes API.

Where the built database differs from the ERD above:

  • 24 tables, not 22: added refresh_tokens (hashed, rotated, reuse detection) and device_tokens (phone push tokens).
  • users.isActive; bag_scans.source / lat / lng; pickup_requests.createdById; invoices.number / dueAt; weighing_records.materialTypeId (optional).
  • Shipment status adds cancelled: created → assigned | collected | cancelled; assigned → created (taken off a planned route) | collected | cancelled; collected → weighed | rejected.
  • A database trigger blocks UPDATE and DELETE on points_ledger; CHECK constraints guard weights, fill level and points.

Phase 2 rules built: a route assigns shipments in one transaction and gives each a 6 digit handover code the customer shows the driver; the driver never sees it. Stops are ordered nearest-neighbour (Google Routes API when a key is set, with fallback). Decision rule v2 collects a bag at least 0.3 full when another open shipment is within 150 m (decision merge).

Known limits: photos sit on local disk uncompressed; warehouse changes are only logged until the audit table (Phase 3); staff-created customers have no password until reset exists; rate limiting is per IP; no "customer not home" button for drivers; real FCM sending not built; stop order ignores traffic and capacity.

Rules for working in parallel

  • Database first, then API, then screens. Nobody changes tables except the Database owner, through a migration.
  • API contract before code. Backend writes the endpoint in Swagger first. Frontend builds against it with fake data, so both work at the same time.
  • One task, one branch, one pull request. Branches come from dev. Another person reviews before merging. main is only what has been tested.
  • Small tasks. A task should take 1 to 3 days. Bigger ones get split.
  • Done means: works on staging, has a test for the business rule, and the Swagger or Figma link is updated.
  • Weekly rhythm: planning at the start of the week, a short check-in in the middle, a demo of something working at the end.
  • Tasks live in Linear. One epic per phase and track, each task with an owner and a size. Blocked tasks are marked and raised at the check-in.
  • Decisions are written down in one place, with the date and who decided.
